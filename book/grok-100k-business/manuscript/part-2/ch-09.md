# Chapter 9: Skills — Encode Your Company's Best Employees Once

The most valuable file in an agent-run company is not a prompt. It is a procedure
that a competent stranger could follow and produce the same output you would. In
Grok Bot that artifact is called a skill, and the documentation is unusually
specific about what it should contain: steps, decision rules, expected output, and
safety boundaries.

Everything in this chapter follows from one sentence in those docs: start with a
one-time task, make it reliable, save the method as a skill, and only then automate
it. That ordering is the difference between a system that compounds and a system
that accumulates folklore.

## Skill, prompt, routine

Three words get used interchangeably and they are not the same object.

A **prompt** is a message. It is consumed once and forgotten.
A **skill** is a reusable set of instructions for how to do a task. It persists, it
is shared across your Bots, and it can be published to a team.
A **routine** tells one Bot **when** to run a workflow: on a schedule, or when
something happens.

The relationship is: routine = skill + trigger + owner. That is why a routine
without a skill is fragile — it runs the same improvisation on a timer.

## The six fields

The documentation lists six things a useful skill states. They map cleanly onto a
file format that survives review:

1. **When to use it** — the trigger condition, in words a router can match.
2. **Required inputs and access** — the systems, the credentials, the format.
3. **The sequence of work** — numbered steps, with decision points marked.
4. **How to validate the result** — the checks that must pass before output ships.
5. **What to return** — the artifact, its path, its schema.
6. **What requires approval** — the actions that stop and wait for a human.

That is the entire specification. Any skill file that omits one of the six will fail
in production for a reason that looks like model quality and is actually
specification quality.

A worked file, trimmed to the essentials:

```markdown
# Skill: Weekly account health

WHEN      Every Monday 08:00, or when asked for "account health".
INPUTS    accounts list (CSV), last 30 days of usage (warehouse), open tickets.
ACCESS    warehouse read-only, ticket system read-only, Slack post (approval).
STEPS
  1. Load the account list; fail loudly if fewer rows than last run by >10%.
  2. For each account, compute: usage delta, open P1/P2 tickets, days since login.
  3. Classify: healthy / watch / at-risk using the rules in `risk_rules.md`.
  4. Draft a one-paragraph note per at-risk account: what changed, what to do.
  5. Post the watch list to #cs-accounts — REQUIRES APPROVAL.
VALIDATE  every account appears once; every at-risk row cites a metric and a date;
          no customer is contacted; no figure without a source.
RETURN    reports/account-health-YYYY-MM-DD.md + a JSON summary for the dashboard.
APPROVAL  any Slack post; any customer contact; any change to risk_rules.md.
```

Two details in that file do more work than the prose. The `VALIDATE` block is what
makes the output checkable by code (Chapter 28 reads it directly). The `INPUTS` row
count check is what catches the most common silent failure in reporting jobs: the
upstream export truncated and the report is confidently wrong.

## Teach by demonstration, then edit

Grok Bot documents a second way to create a skill: demonstrate the workflow once in
a Bot's computer view, and the Bot records it. The documented limits are worth
knowing precisely, because they bound what you can expect.

- Teaching records visible computer interaction for up to ten minutes.
- It does not record microphone audio.
- The learned skill is a **draft**.

That last word is the whole chapter. A demonstration captures what you did, not why.
It cannot see the rule you applied when a value looked wrong, the customer you
skipped because they are in a legal dispute, or the exception you make every March.
So the workflow is: demonstrate, then add decision rules, failure handling and
approval boundaries that were not visible in one example. The demonstration gives
you the skeleton in two minutes; the editing gives you the employee in an hour.

One caution from the documentation that deserves emphasis: avoid exposing secrets
during the demonstration, and use the secure handoff flow for credentials. A
recording is a recording.

## Routines: the trigger is the product

A routine tells one Bot when to run. Documented triggers are schedules and events:
a Slack message, a GitHub, Linear, Sentry or PagerDuty event, an email to the Bot's
own address, or a webhook call.

When you create one, confirm six things explicitly, because the Bot will otherwise
infer them:

- the owning Bot
- the schedule and time zone
- the input source
- the expected result
- the approval boundary
- what should happen when a source is missing

That last item is where most routines fail in week two. The documented example is
the right shape: "If the source data is unavailable, report the failure instead of
using old data." Without that sentence, an agent facing a stale export will happily
report yesterday's numbers as today's.

Two scheduling details surprise people. A new routine waits for its next scheduled
time; it does not run on creation, so a job created at 08:05 for "daily at 08:00"
first runs tomorrow. And schedules must be at least five minutes apart.

## Rate limits and the cost of cadence

Routines are not free and they are not unlimited. The documented limits:

| Limit | Value |
|---|---:|
| Routines per Bot | 50 |
| Run records kept per routine | 20 most recent |
| Minimum spacing between schedules | 5 minutes |
| Total runs across your routines | 300 per hour |
| Runs per individual routine | 200 per hour |

Every run spends usage, which means a routine is a recurring cost with a cadence
you chose. An hourly routine that takes four minutes of agent work is roughly 720
runs a month; a five-minute routine is 8,640. This is the quiet way to spend a
week of budget in a day, and the documentation says so plainly: widen schedules and
narrow triggers before you raise a plan.

The practical rule: **a routine's frequency should be set by how often the
underlying facts change, not by how often you would like to be reassured.** Account
health changes weekly. A dashboard refresh does not need to be every five minutes
unless someone is watching it.

## Event triggers need narrow matching

Event triggers are more powerful than schedules and correspondingly easier to
misconfigure. The documented guidance is to define a narrow matching rule and a
clear response, and to avoid broad listeners like "every new message."

A good trigger names a channel and a phrase:

> When a message in `#customer-escalations` contains a support ticket link and the
> phrase "needs repro," open the ticket, reproduce the issue in staging, and post a
> repro pack in this conversation. Never post back to Slack without approval.

A bad trigger is any message in a busy channel, which will run constantly, spend
usage, and eventually act on something irrelevant.

For webhooks, the documented mechanics are: the routine exposes a POST URL, a key,
and a ready-to-copy `Authorization: Bearer <key>` header. A `200` means the call was
accepted and a run started — not that the work finished. Any other response means
no run started, so check that the routine is not paused and that you are using the
current key.

## The golden sample

A skill without a regression sample is a rumour. The sample is ten inputs and ten
expected outputs, plus the specific failure you are most afraid of.

Keep it in the same repository as the skill, in a folder named `golden/`. After any
edit to the skill — a new rule, a changed format, a model upgrade — run the ten and
diff. This is not a formality. Model behaviour changes when the model changes, and
your skill's quality is a property of the pair, not of the text alone.

Three checks belong in the golden set for almost every business skill:

1. **The empty input.** Zero rows should produce a clear "no data" artifact, not a
   report full of invented zeros.
2. **The duplicate input.** The same item twice should not produce two outputs.
3. **The anomaly.** One value that is wildly out of range should be flagged, not
   averaged in.

If the skill passes those three and the ten normal cases, it is ready to be
scheduled.

## Publishing skills to a team

If you belong to a team, skills can be published so teammates and their Bots can
use them. The documentation requires a description before publishing, because
teammates and their Bots use the description to decide when the skill applies.
After publishing, the menu offers Sync to push later edits, Copy link, and
Unpublish. Skills that shipped with an app or a Bot's template cannot be published.

The operational consequence: **the description is part of the interface**. A vague
description means the skill will not be discovered, which means the team will
rebuild it, which means you now have two versions and no single source of truth.

## Four anti-patterns

**The novel.** A 2,000-word skill with no numbered steps and no validation. It reads
like a job description and behaves like a lottery.

**The demo capture shipped as-is.** A recorded skill with no decision rules. It
works on the exact case demonstrated and fails on the eleventh.

**The hidden dependency.** A skill that assumes a file exists because it existed
when you wrote it. Every input must be named and checked.

**The routine with no owner.** A schedule running against a system nobody is
responsible for. When it breaks, it breaks quietly. Every routine needs a named
human in the skill file, even if the file is written for a machine.

## The skill lifecycle

A skill is not a document, it is an object with a lifecycle, and treating it that
way prevents the most common operational failure: skills that were correct in March
and are wrong in November, still running.

**Draft.** Written from a real task you just did by hand. Contains the six fields.
Has no schedule.

**Tested.** Run against the golden set, plus the three edge cases (empty, duplicate,
anomaly). The definition of done is checked by code, not by eye. Still no schedule.

**Scheduled.** Attached to a routine with an owner, a cadence and an approval
boundary. From this point the skill has real consequences.

**Frozen on failure.** When the golden set fails twice in a row, the routine pauses
automatically. A skill that fails its own regression test must not keep running on a
timer; that is how a small bug becomes a weekly incident.

**Retired.** Replaced by a newer version or no longer needed. Retired skills move to
an `archive/` folder rather than being deleted, because the artifacts they produced
still exist and someone will eventually ask how they were made.

The lifecycle is enforceable with a field in the skill header and a check in the
runner. It sounds bureaucratic for a one-person business until the first time a
skill silently rots against a changed API and produces three weeks of wrong reports.

## Measuring skill quality

Four numbers, tracked per skill, tell you whether it is getting better.

**Exception rate.** The share of runs that need human correction. This is the number
that determines your capacity (Chapter 4), so it is the one to optimize.

**Edit distance.** Words a human changed per thousand produced. For drafting skills
this is more sensitive than a pass/fail count, because it moves before the skill
fails outright.

**Repeat-error rate.** How often the same mistake appears twice. A repeat error means
the correction was not written back into the skill, which is a process failure rather
than a model failure.

**Cost per successful artifact.** Total run cost divided by runs that passed
validation. This is the number to compare against a human baseline, and it punishes
retry-heavy skills that look cheap per call.

A skill with a falling exception rate, falling edit distance, no repeat errors and a
stable cost per artifact is improving. A skill with a flat exception rate and rising
cost is thrashing, and the fix is usually to narrow the scope rather than to add
instructions.

## The skill registry

Once you have more than about five skills, you need an index, because the failure
mode of a skill library is not bad skills — it is duplicate skills with slightly
different rules.

The registry is a small file with one row per skill: name, owner, version, status,
trigger, systems touched, approval boundary, last golden-set run, and a one-line
description. Two rules keep it honest.

**One owner per skill.** Not a team, a name. The owner is who gets the alert when the
golden set fails.

**One skill per job.** If two skills claim the same trigger, one is wrong. Resolve it
before a routine picks the wrong one at 3 a.m.

The registry also gives you something that is genuinely hard to buy: a map of what
your business can actually do without you. That map is the asset, far more than any
individual prompt.
