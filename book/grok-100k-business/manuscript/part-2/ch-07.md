# Chapter 7: Grok Bot — Put a Brain Behind the Business

A business run by agents needs one thing above all others: a planner that can hold
a goal across more than one step. Everything else in this part of the book is
machinery around that planner. The machinery is replaceable. The planner is what
determines whether you have an employee or an expensive autocomplete.

Grok Bot is documented as a proactive AI teammate: an agent with access to a real
computer in the cloud, a browser, a filesystem and a terminal, working across apps
and websites, reachable by chat or voice, able to run on a schedule, able to
remember your preferences and logins, and able to hand work to another Bot. That
description is worth reading twice, because it describes a **worker with a desk**,
not a chat window with opinions.

## What the brain actually does

A chat model maps a prompt to a response. A planner maps a goal to a sequence of
actions, where each action changes the world and changes what should happen next.
The loop is short and it repeats:

```
observe  ->  decide  ->  act  ->  verify  ->  observe
```

Four properties separate a real planner from a prompt.

**It decomposes.** "Close the month" becomes: pull the export, reconcile against
the ledger, list the twelve unmatched rows, draft the variance note, request the
two missing invoices. A model that answers "close the month" with a paragraph has
not decomposed anything.

**It chooses tools by name.** Not "use the database" but "call `ledger.read` with
account 4010 and period 2026-10." Tool choice is where a plan becomes executable.

**It reads the result.** The important sentence in the loop is the one after the
tool returns. Did the write succeed? Was the value the expected type? Did the query
return zero rows because there is no data, or because the filter is wrong? Models
that skip this step are the ones that report success after a 403.

**It re-plans.** The tenth step is usually wrong when the job started, because the
first tool call taught you something. A planner that cannot revise is a workflow
with a language model bolted on, and it will fail on the first surprise.

## Choosing the brain

Two documented models cover most of this book's work, and they are priced
differently for good reasons.

| Model | Context | Input / 1M | Cached in / 1M | Output / 1M | Use it for |
|---|---:|---:|---:|---:|---|
| `grok-4.7` | 500K | $2.00 | $0.50 | $6.00 | planning, judgment, writing, anything with ambiguity |
| `grok-build-0.1` | 256K | $1.00 | $0.20 | $2.00 | code-shaped work: patches, scripts, structured transforms |

Those are the sub-200K prices, and the qualifier is doing real work: both models
switch to double rates once the prompt reaches 200K tokens, so the cliff described
below applies to the coding model too.

The decision rule is not "use the best model." It is **where does judgment live in
this job?** If the answer is "in choosing what to do," pay for the expensive model
at the planning step. If the answer is "nowhere, the shape is known and the
content is mechanical," route to the cheaper model and spend the savings on
volume.

Three routing patterns that hold up:

**Plan expensive, execute cheap.** A 500-token planning call on the strong model
produces a task list; each task is executed by the cheap model with a tight
instruction. You pay judgment prices for judgment and extraction prices for
extraction.

**Escalate on uncertainty.** The cheap model runs first; if its confidence signal
or a mechanical check fails, the task re-runs on the strong model. Most tasks never
escalate, so the blended cost stays near the cheap rate while quality stays near
the strong one.

**Two-pass verification.** The cheap model produces; the strong model reviews
against a rubric. This is more expensive than a single strong call and cheaper
than a human review, and it catches the class of error that matters: plausible
output that violates a rule.

## The context cliff

The pricing table has a second row that most operators miss. Above a threshold
prompt size — 200K tokens for the 4.7 family — every token in the request is
billed at double: $4 per million in, $12 per million out.

This is a cliff, not a slope. A request at 199K tokens costs half what the same
request costs at 201K. And because the rule applies to the whole request, not the
excess, the marginal cost of crossing the line is enormous:

```
199,000 tokens in  × $2.00 / 1M = $0.398
201,000 tokens in  × $4.00 / 1M = $0.804
```

One thousand extra tokens of context doubled the bill. In practice this means your
context budget is a hard engineering constraint, not a comfort feature. If a job
needs 250K tokens of context, it needs to be decomposed into sub-tasks, cached
prompts, or a retrieval step — not run as one heroic call.

The caching discount is the other half of the same coin. Cached input is documented
at $0.50 per million for `grok-4.7`, a quarter of the fresh-input price. That means
a stable prefix — instructions, schema, rubric, brand guide — should be identical
across runs and placed at the front, so the provider can serve it from cache. A
variable suffix at the end costs full price and is usually a small fraction of the
prompt.

## What the brain must never decide

Two decisions belong outside the model, and putting them inside is the most common
architecture mistake in this entire category.

**Whether it may act.** Permission is a property of the system, not a judgment of
the planner. A model that is asked "should I send this email?" will sometimes
answer yes, and it will be persuasive about it. The approval gate (Chapter 12) must
be enforced by code that the model cannot talk its way past.

**Whether its own output is correct.** Self-assessment is not verification. A model
that graded its homework would be right about as often as it is confident, which is
to say often enough to be dangerous. Correctness is established by an independent
checker: schema validation, arithmetic, cross-file consistency, a test, a human
sample. Chapter 28 turns this from a principle into an operating discipline.

Everything else — tone, structure, prioritization, which of three plausible
approaches to take — is fair game for the brain. That is the division of labour:
the model decides *what*, the system decides *whether*.

## Instrumentation: what to log on every run

You cannot manage what you cannot measure, and the model layer is where costs hide.
Log five things on every call:

1. **Prompt size in tokens**, split into cached and fresh. This is the number that
   predicts your bill.
2. **Output size in tokens.** Output costs more than input — three times as much on
   `grok-4.7`, double on `grok-build-0.1` — so a verbose model is an expensive one.
3. **Tool calls**, with name and duration. Tools are usually the dominant cost in
   retrieval-heavy work.
4. **Stop reason.** A run that stopped because it hit a token ceiling is a failed
   run that looks successful.
5. **Retries.** A retried call is a paid call that produced nothing.

With those five fields you can answer the only question that matters at the end of
a month: which job is expensive, and why. Without them, you have a bill and a
feeling.

## The four failure modes of a planner

**Drift.** The agent starts on the assigned job and ends up doing something related
but unrequested — "while I was in there, I also updated the summary." The fix is a
job boundary written into the skill and a diff review that catches files outside
the declared scope.

**Premature stop.** The agent reports success after the easy half. It created the
report but did not send it; it drafted the email but did not schedule it. The fix
is a definition of done that names the final artifact and its location, plus a
check that the artifact exists.

**Tool thrash.** The agent calls the same tool six times with slightly different
arguments, burning cost and time. The fix is a per-tool call budget and an
instruction to escalate after two failures rather than retrying indefinitely.

**Confident wrongness.** The most expensive mode. The output is well-formed,
plausible, and false. There is no prompt that fixes this, because the model has no
access to the ground truth. The fix is external: a source of truth to check
against, a verifier that compares artifacts, and a sample review by someone who
knows the domain.

Notice that three of the four are fixed by constraints rather than intelligence.
That is the recurring lesson of this part of the book: a mediocre planner inside a
tight system beats a brilliant planner inside a loose one.

## Writing a goal the brain can hold

A goal is not a wish. It has four parts, and a planner that receives fewer than
four will improvise the missing ones — usually badly.

```
GOAL:     Reconcile the November invoice export against the ledger and produce
          a variance memo.
ARTIFACT: reports/2026-11-variance.md, plus a list of unmatched invoice ids.
DONE:     Every invoice id in the export appears in the memo as matched or
          unmatched, and each unmatched id has a reason from the allowed set.
LIMITS:   Read-only on the ledger. No emails. Stop after 40 tool calls and
          escalate with what is known.
```

The `LIMITS` block is what makes the goal safe to hand to a machine. The `DONE`
block is what makes it testable. Neither can be inferred from the job title, which
is why every skill in Chapter 9 states its inputs, its output artifact and its
approval boundary before it states a single step.

## Why this chapter comes before the hands

It is tempting to start with the execution layer — install the CLI, run the command,
watch it edit a file. That order produces a demo. This order produces a business,
because the planner is the part you reason about, price, and constrain. The hands
are commodity. The goal, the limits and the definition of done are the intellectual
property.

## Routing in practice

Routing sounds abstract until you price it. Three worked cases from service work
show the pattern.

**Case one: the weekly account-health report.** The judgment is in the
classification — which accounts are at risk and why. That is one planning call per
account on the strong model, roughly 800 tokens in and 200 out, so about
three-tenths of a cent per account. The rest of the job — formatting, chart data,
the digest — is deterministic code. Total model cost for fifty accounts: about
fifteen cents.
Routing here means "use the strong model for the classification only, and stop
calling a model for the arithmetic."

**Case two: the research memo.** Planning is cheap (one call to decide the
sub-questions), execution is expensive because of tools, and synthesis benefits from
the strong model. The right shape is cheap-model extraction per source, strong-model
synthesis at the end. A naive implementation uses the strong model for every source
summary and pays three times as much for a slightly worse result, because
summarizing one page does not require judgment.

**Case three: the code-shaped transform.** Renaming a field across forty files is
not a judgment task. It is a pattern-matching task with a test at the end. The coding
model is documented at half the price of the flagship and is the correct choice. The
test is what makes it safe; the model choice is what makes it cheap.

The general rule: **route by the location of ambiguity, not by the importance of the
job.** Important jobs with no ambiguity are cheap. Unimportant jobs with ambiguity
are not.

## The planner as a state machine

A planner that is allowed to loop freely will eventually loop. The fix is to make
the states explicit, so an execution can be inspected and resumed.

Five states cover most jobs: `plan`, `act`, `verify`, `escalate`, `done`. Each
transition has a guard. `plan → act` requires a non-empty task list. `act → verify`
requires at least one tool result. `verify → done` requires the checks in the skill's
validation block to pass. `verify → escalate` fires on a failed check, a budget
exhaustion, or a missing input. Any state can go to `escalate` on error.

Two properties follow from writing it this way. First, resumption is trivial: the
state and the artifacts are on disk, so a crashed run continues rather than
restarting. Second, the failure is visible: a run stuck in `act` for forty minutes is
thrashing, and a run that reached `done` without passing `verify` is a lie the state
machine refuses to tell.

You do not need a framework for this. A JSON file with the current state and a
handful of transitions is enough, and it is far easier to debug than an agent
framework's internal loop.

## Prompt architecture

The order of the prompt is a cost decision and a quality decision at the same time,
because providers cache stable prefixes.

Put the invariant material first: the role, the rules, the output schema, the rubric.
Put the variable material last: today's data, the specific request, the previous
step's result. This gives the cache the best chance of a hit and keeps the expensive
fresh tokens to the part that actually changed.

Three habits that consistently improve output:

**State the artifact, not the activity.** "Write `reports/x.md` with these six
sections" beats "analyze the data." The model will match a shape it can see.

**Give one worked example of good and one of bad.** A single contrast pair does more
than a paragraph of adjectives, and it costs a few hundred cached tokens.

**Name the escalation condition.** "If the export has fewer rows than yesterday,
stop and report the discrepancy" is a sentence that prevents the most common silent
failure. A model that is not told when to stop will improvise.

## When the brain is the wrong tool

Three jobs that look like model work and are not:

**Arithmetic.** Totals, deltas, percentages and reconciliations belong in code. A
model doing arithmetic is a random number generator with good manners.

**Routing by exact match.** If the job type is determined by a field value, use a
dictionary lookup. A model-based router is for ambiguous cases only.

**Formatting.** Deterministic templates produce identical output every time, and
identical output is what makes a diff reviewable.

The discipline is to ask, for each step, "could a competent engineer write this
without a model?" If yes, they should. The model's value is in the steps where the
answer depends on meaning.

## The brain's operating budget

Finally, a number to hold in mind. At documented rates, a planning call of 1,000
tokens in and 250 out costs $3.50 per thousand calls. A synthesis call of 30,000
tokens in and 2,000 out costs $72 per thousand — same vendor, same model, roughly
twenty times the bill, and the only difference is how much context each call carries
and how much output it is allowed to produce. On a $100 deliverable, that is a 96%
gross margin or a 28% one, and nothing about what the customer pays has changed.

Chapter 8 gives the brain hands, and the first thing it does is make the hands
boring: same directory, same output path, same receipt, every run.
