# Chapter 10: MCP — Give Your Agent Keys to Systems That Matter

An agent with no connectors is an agent with opinions. The moment it can read your
CRM, your warehouse, your inbox and your ledger, it can do work. The moment it can
write, it can do damage. MCP is the interface where that trade is made, and it
deserves more care than any other part of the stack, because everything else is
recoverable.

The Model Context Protocol is an open standard for exposing tools and data to a
model in a structured, reviewable way. In this stack it is the documented path for
custom tooling: Grok Bot supports interacting with any MCP server or API, and Grok
Build discovers MCP servers in a project — along with config sources, instructions,
skills, plugins and hooks — through `grok inspect`.

That last command is worth more attention than it gets. Before you trust an agent
in a repository, run it and read what the agent will see. Every connector is a
capability, and every capability is a permission.

## The connector inventory

Start with a table, not a server. For each system, write down four things: what the
agent reads, what it writes, why it needs it, and what happens when it is wrong.

| System | Access | Why | Failure mode if wrong |
|---|---|---|---|
| Warehouse | read-only, one schema | metrics for reports | confident wrong numbers |
| CRM | read + note-write | context, logging | silent data pollution |
| Inbox | read + draft | triage, reply drafts | sending to the wrong thread |
| Ledger | read-only + note | reconciliation | duplicated entries |
| Calendar | read + propose | scheduling | double-booking a customer |
| Docs | read + draft | source material | stale policy quoted as current |

Two rules fall out of the table.

**Read-only until proven otherwise.** A connector starts read-only and stays there
until a specific, written job requires a write. "It would be easier" is not a
requirement.

**One system, one purpose.** If the same credential reaches the CRM and the billing
system, a mistake in one becomes a mistake in both. Separate tokens cost nothing
and bound the blast radius.

## Cost per call is a design parameter

Documented tool pricing turns connector design into an economic decision:

| Tool | Cost |
|---|---:|
| Web search | $5 per 1,000 calls |
| X search | $5 per 1,000 posts, $10 per 1,000 profiles |
| Code execution | $5 per 1,000 calls |
| Collections / file search | $2.50 per 1,000 calls |
| File attachments | $5 per 1,000 calls |
| Remote MCP tools | token-based, set by the server |

Two things follow. First, a research job with twenty searches costs ten cents before
the model has written a word — the tools, not the tokens, set the unit cost of
retrieval-heavy work. Second, a domain-specific MCP server is often cheaper than
general web search, because it returns eight relevant records instead of eighty
irrelevant ones. Precision is a cost lever.

The practical budget rule: **cap calls per job, not tokens per job.** A ceiling on
searches forces the agent to synthesize what it has or escalate, which is exactly
the behaviour you want. An instruction to "be concise" does nothing to a loop that
has already decided to search again.

## Credentials: the part that decides your worst day

Every connector is authenticated, and the authentication design is where
one-person businesses get hurt. Five rules, in order of importance.

**1. Per-agent tokens.** Not one admin token shared by five agents. If an agent is
compromised, or simply misbehaves, you revoke one token and the others keep
working.

**2. Least privilege, expressed in scopes.** Read-only where read-only is enough.
One schema, not the whole warehouse. One mailbox, not the domain.

**3. Short expiry.** Tokens that expire weekly force a review. Tokens that never
expire become permanent invisible infrastructure.

**4. A tested revocation path.** Not "we can revoke it" — a document with the exact
steps, tested quarterly. The first time you need it will be under pressure.

**5. No credentials in prompts or files.** Environment injection at run time, or a
secret manager. A credential pasted into a skill file is a credential in your git
history forever.

The documentation for Grok Bot adds a useful pattern on the human side: credentials
can be collected through a secure form or vault so the value is filled into the page
without being shown to the model. That is the right instinct — the agent should be
able to *use* a secret without being able to *read* it.

## The read-then-write ladder

Introduce any connector in four stages, and do not skip a stage because the first
one worked.

**Stage 1 — read, report only.** The agent reads and produces a report. No writes
anywhere. This is where you learn whether the data is what you think it is.

**Stage 2 — read, draft write.** The agent produces the exact write it would make,
as a diff or a payload, and does not apply it. You review. This is where you learn
whether its judgment matches yours.

**Stage 3 — write with approval.** The write is applied after a human approves the
specific action. This is where the approval card earns its keep.

**Stage 4 — write with audit.** The write runs unattended, with a receipt, a diff
and a sampled review. This is where the business scales, and it is only safe after
stages 1–3 have produced an error rate you can live with.

Most operators try to jump from 1 to 4 because stage 2 feels like busywork. Stage 2
is the cheapest place in the entire lifecycle to discover that the agent's definition
of "update the record" includes overwriting a field nobody asked about.

## Failure taxonomy

Connectors fail in five ways, and each wants a different response.

**Timeout.** Retry once with backoff, then escalate. Never retry a write blindly;
check whether it landed first.

**Rate limit (429).** Back off with jitter. If the job hits the limit regularly, the
job's cadence is wrong, not the API.

**Auth expiry (401).** Stop immediately and alert a human. Retrying an expired token
is how you lock an account.

**Empty result.** The most dangerous failure, because it looks like success. A query
that returns zero rows should be treated as an anomaly until proven otherwise —
check row counts against the last run.

**Schema drift.** A field renamed upstream. The agent will happily map the wrong
column. Pin the schema, validate on read, and fail loudly when a required field is
missing.

The general principle: **distinguish "no data" from "no answer."** An agent that
cannot tell the difference will fill the gap with prose.

## The audit question

Before you ship any connector, answer this: *can I reconstruct, from logs alone,
everything this agent read and wrote last Tuesday?*

If the answer is no, you do not have an auditable system. You have a system that
works until it doesn't, and then you have a conversation with a customer in which
you guess.

The minimum log per call: timestamp, tool name, target, argument hash, result code,
row count or payload size, duration. Arguments themselves may contain customer data,
so hash or redact them and keep the full payload only where retention rules allow.

## Anti-patterns

**The god token.** One credential with access to everything, used by every agent,
because provisioning was annoying. This is the single most common cause of a
catastrophic incident in small agent deployments.

**The marketplace reflex.** Installing an MCP server because it exists. Every server
is code running with your credentials. Read it, or run it in a container with a
scoped identity.

**Tool sprawl.** Forty tools available to an agent that needs four. Tool selection
degrades as the menu grows, and every unused tool is an attack surface. Give each
agent the smallest set that completes its job.

**The silent reader.** A connector that reads customer data into a prompt that is
then logged in full. Data protection is not only about where the data is stored; it
is about where it flows.

## Reviewing an MCP server before you trust it

An MCP server is code that runs with your credentials and returns text that a model
will treat as instructions. That combination deserves a review, even when the server
came from a marketplace you like.

Six questions, in order:

**1. What does it expose?** List every tool, every resource, and whether each is read
or write. A server that exposes one search tool is a different risk from a server
that exposes an admin API.

**2. What does it authenticate with?** A scoped token you created, or your account
password, or an OAuth flow that grants broad scopes? The narrower the credential, the
less you need to trust the code.

**3. Does it execute anything?** Servers that run shell commands, evaluate code, or
write to a database are a different category from servers that fetch documents. Treat
execution servers as you would treat a CI runner: isolated, scoped, logged.

**4. Where does the data go?** A local server keeps data on the machine. A remote
server sends your queries and results to someone else's infrastructure. Both can be
acceptable; only one requires a data-processing conversation with your customer.

**5. What does it return, and can that text carry instructions?** Any server returning
content from the open web is a prompt-injection vector. The defence is architectural
— untrusted text never carries authority — not a warning in the prompt.

**6. How do you revoke it?** If the answer is "delete the config," check whether the
credential still exists in the source service. It usually does.

The review takes twenty minutes and it is the difference between a connector and an
open door.

## Thin connectors beat clever ones

When you cannot find a server, the instinct is to build a rich one: list, search,
create, update, delete, bulk operations. Resist it.

A thin connector — one read tool and one write tool, with a narrow schema — is safer,
cheaper for the model to use, and easier to test. Tool selection quality degrades as
the menu grows; an agent choosing between four tools makes better choices than an
agent choosing between twenty.

The pattern that works: build the read path first and use it for a month. Add the
write path only when a specific job requires it, and add a single write tool rather
than a CRUD suite. If a job needs bulk operations, that is a signal the job should be
done in code with the connector as a data source, not through tool calls.

There is a cost argument too. Every tool definition consumes prompt tokens on every
call, and a large tool menu can add thousands of tokens per request. On a
high-frequency job, a trimmed tool set is a direct margin improvement.

## Retention, residency, and the flows nobody documents

Data protection is usually discussed as storage: where is it kept, how long, who can
read it. In an agent stack, the harder question is flow: where does the data go
during a single run?

A realistic flow for one customer record: read from the CRM, sent to the model
provider as prompt tokens, echoed into a log file, embedded in a report, cached by
the provider for some window, and copied into the agent's workspace on a shared
cloud computer. That is six locations from one read.

You do not need a compliance department to handle this. You need three decisions,
written down:

**Which data is allowed in a prompt at all.** A whitelist per job. If a field is not
needed, it is not sent — and the connector should not return it.

**How long the agent's workspace keeps copies.** A retention window with a job that
deletes, not a policy that hopes. The platform documentation is explicit that
deleting an agent does not remove files from the shared computer; the cleanup is
yours to run.

**What the customer is told.** One paragraph: what is read, what is sent to a model,
how long it is kept, how to request deletion. It is the same paragraph you will be
asked for in every enterprise sales cycle, so write it once.

The distinction between "we store it securely" and "here is the flow, and here is the
deletion job" is the difference between a vendor and a supplier.
