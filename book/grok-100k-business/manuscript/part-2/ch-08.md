# Chapter 8: Grok Build — Give the Brain Hands and Let It Actually Work

A planner without hands is a consultant. It can tell you what to do and it cannot
do it. Grok Build is the layer that changes files, runs commands, and leaves an
artifact behind — and the way you wire it determines whether you have an employee
or a very fast way to corrupt a repository.

Documented surfaces, from the Grok Build overview: an interactive terminal UI, a
headless mode for scripts and bots, and the Agent Client Protocol for use inside
other applications. Installation is a single command on macOS and Linux, a
PowerShell line on Windows, and first launch opens a browser for authentication
unless you set an API key.

```bash
curl -fsSL https://x.ai/cli/install.sh | bash
cd your-project
grok
```

That gets you the demo. This chapter is about the part after the demo.

## Three surfaces, three risk profiles

| Surface | Who drives | Best for | Blast radius |
|---|---|---|---|
| Interactive TUI | You, in real time | exploration, one-off repairs, teaching | one session, one directory |
| Headless (`grok -p`) | A scheduler, script or queue | recurring jobs, batch work | whatever the process can touch |
| ACP | Another application | embedding the agent in your own tool | inherited by the host app |

The TUI is where you learn what the agent does. Headless is where the business
lives, because headless is the only surface that can run without you. ACP matters
if you are building a product; most operators never need it.

The risk profile column is the one to internalize. An interactive session has a
human watching, which is a real control. A headless run has no human at all, so
every permission the process has becomes the agent's permission. That is why the
sandbox section below is not optional.

## The headless contract

A headless invocation is a function call with a language model inside. Treat it
like any other function: declare inputs, declare outputs, bound the runtime, and
check the result.

```bash
grok -p "Reconcile exports/invoices-2026-11-17.csv against the ledger and write
reports/recon-2026-11-17.md. Read-only on the ledger. Stop after 40 tool calls." \
     --output-format streaming-json
```

Four things make that line production-worthy rather than a demo.

**One working directory per job.** The agent should start in a directory that
contains only that job's inputs and outputs. If it wanders, the damage is confined
to a folder you can delete.

**An explicit output path.** "Write the report" is not a contract. "Write
`reports/recon-2026-11-17.md`" is. The path is checkable after the run, which is
how you distinguish success from a confident summary.

**A bounded run.** A token ceiling and a tool-call ceiling. When either is hit, the
process exits non-zero and the job escalates. An unbounded run is a cost incident
waiting for a slow API.

**A machine-readable stream.** `--output-format streaming-json` is documented and it
is what lets a wrapper distinguish "the agent finished" from "the agent printed
something and died." Parse the stream, do not scrape stdout.

## A wrapper that survives contact with reality

The following is the shape that has held up. It is deliberately boring: a timeout,
a working directory, a receipt, and a check that the artifact exists.

```python
import hashlib, json, subprocess, sys, time
from datetime import datetime, timezone
from pathlib import Path

def run_job(job_dir: Path, instruction: str, artifact: Path, timeout_s=900):
    started = time.time()
    proc = subprocess.run(
        ["grok", "-p", instruction, "--output-format", "streaming-json"],
        cwd=job_dir, capture_output=True, text=True, timeout=timeout_s,
    )
    ok = proc.returncode == 0 and artifact.exists()
    receipt = {
        "run_id": datetime.now(timezone.utc).strftime("%Y%m%dT%H%M%SZ"),
        "job_dir": str(job_dir),
        "artifact": str(artifact),
        "sha256": hashlib.sha256(artifact.read_bytes()).hexdigest() if artifact.exists() else None,
        "returncode": proc.returncode,
        "seconds": round(time.time() - started, 1),
        "verdict": "complete" if ok else "failed",
        "stderr_tail": proc.stderr[-500:],
    }
    (job_dir / "receipts").mkdir(exist_ok=True)
    (job_dir / "receipts" / f"{receipt['run_id']}.json").write_text(json.dumps(receipt, indent=2))
    return receipt
```

Two details in that code matter more than they look.

**The artifact check is separate from the exit code.** An agent can exit zero after
writing nothing. The existence check and the hash are what make the receipt
evidence rather than a claim.

**The receipt is written by the wrapper, not the agent.** Anything the agent writes
about its own success is testimony. Anything the harness writes is a measurement.
Keep the two in separate files and trust the second one.

## Two kinds of hands

There are two execution surfaces in this stack, and confusing them is a common
source of security mistakes.

**Grok Build runs locally, in a directory you choose, with your user's
permissions.** That is convenient and it means the agent can read anything your
shell can read. Treat it like a contractor sitting at your desk: fine for a
project directory, unacceptable with production credentials in the environment.

**Grok Bot's Bots share a persistent cloud computer** — browser, filesystem,
terminal — documented as one machine per user account, shared across your Bots.
Convenient for browser work and for long-running jobs that survive closing your
laptop. The documented consequence is important: files, browser sessions and
command-line credentials on that machine are available across your Bot roster, and
the documentation says plainly that separate Bots are not a security boundary.

So the rule is: choose the machine based on what it can reach, not based on which
one is faster. Sensitive client data belongs on a machine with a scoped identity
and nothing else on it.

## Sandboxing the hands

An agent that can write files needs three boundaries before its first production
run.

**Filesystem scope.** One job directory, mounted or created per run, wiped or
archived afterwards. The agent never sees a parent directory with other clients'
data in it. If the job needs reference material, copy it in.

**Credential scope.** No ambient credentials. The process gets exactly the tokens
its tools need, injected at run time, with the shortest possible expiry. If the
agent can read `~/.aws` or a `.env` from the repo root, you do not have a sandbox;
you have a shared account with extra steps.

**Network scope.** An allowlist where the platform supports it. In practice, at
minimum: no outbound access to internal admin panels, and every external call
logged by the tool layer rather than by the model.

There is a fourth boundary that is not technical: **the agent does not get write
access to the directory where the business records live.** Reports are written to a
staging path and promoted by a separate step after the verifier passes. Promotion
is a code path, not a judgment.

## Idempotency, or why reruns must be safe

Any job that runs on a schedule will run twice for the same input eventually: a
retry after a timeout, an overlapping schedule, a manual re-run to reproduce a bug.
If the second run duplicates its side effects, you have a data quality incident.

Three rules make a job idempotent:

1. **Name outputs by input identity**, not by timestamp. `recon-2026-11-17.md`
   overwrites cleanly; `recon-2026-11-17-v2-final.md` accumulates.
2. **Write before you notify.** The artifact is the source; the notification is
   derived. A rerun regenerates the artifact and re-sends the same message, which
   is annoying but not corrupting.
3. **Never append to a business ledger from the agent.** Append a note with the run
   id, or write to a staging table that a deterministic job merges. The merge is
   where deduplication belongs, because it can be tested.

## What to log about the hands

The brain chapter logged tokens. The hands chapter logs actions. At minimum: tool
name, target, duration, result code, and whether the action was a read or a write.
For writes, the diff or a hash of the affected object.

This is what makes the receipt chain in Chapter 3 real. Without action-level logs,
the receipt is a claim. With them, it is an audit trail.

## The failure modes that bite first

**Permission creep by convenience.** The first week, the agent runs with a scoped
token. The second week, a task needs one more scope, so it gets the admin token
"temporarily." Six months later the temporary token is the only one that works.
The fix is a review cadence: every credential re-justified monthly, and a rule that
scope changes require a commit.

**Silent partial completion.** The agent processes 40 of 50 items and exits zero.
The fix is a count check in the wrapper: expected items in the input, processed
items in the output, difference escalated.

**The wandering working directory.** The agent writes outside the job directory
because a path in the prompt was absolute. The fix is to never put absolute paths
in a prompt; use relative paths inside the job directory and let the wrapper
resolve.

**Timeout as success.** The process is killed at 900 seconds, the artifact from a
previous run is still there, and the existence check passes. The fix is to clear or
version the artifact path at the start of each run, and to check the receipt's
timestamp.

## The rule that makes all of this worth it

Every one of these controls costs minutes to build and saves a customer. That is the
entire economic argument for the fence: the expensive failures in agent-run
businesses are not subtle, they are ordinary software failures that nobody bothered
to prevent because the demo worked.

## The job directory

The single most effective sandbox is a directory that contains exactly what the job
needs. Its shape is boring on purpose:

```
jobs/invoice-recon-2026-11-17/
  in/            # inputs, read-only to the agent
  work/          # scratch space
  out/           # the artifact, the only thing promoted
  receipts/      # written by the wrapper
  RUN.md         # the goal, the limits, the definition of done
```

Four properties make this worth the five minutes it takes to create.

**`in/` is a copy.** Never point the agent at a live share or a synced folder. If the
job needs three files, copy three files. Copied inputs are reproducible; a live
folder is a moving target.

**`out/` is the only promoted path.** Whatever the agent writes elsewhere is
discarded. Promotion copies `out/<artifact>` to the delivery location after the
verifier passes. This is the code path that replaces "the agent said it was done."

**`RUN.md` is the contract.** It repeats the goal, limits and definition of done from
the skill, so a human reading the folder later knows what was supposed to happen
without opening a chat transcript.

**`receipts/` is append-only.** Even when the run fails. Especially when the run
fails.

The directory also solves the wandering-path problem: every path in the prompt is
relative, so there is no way for the agent to write outside the job folder unless
something has gone very wrong upstream.

## Three ways to trigger a job

Scheduling is a solved problem; the mistake is picking the wrong mechanism.

**Cron or systemd timer.** Simplest, runs on a machine you control, no platform
dependency. Use it for internal jobs where a missed run is inconvenient rather than
expensive.

**A workflow runner (GitHub Actions or equivalent).** Good when the job touches a
repository, needs a fresh environment per run, and should leave a visible log. The
runner provides isolation, secrets management and retention almost for free.

**A platform routine.** Documented in Grok Bot: schedule or event, owned by a Bot,
runs in the cloud while your laptop is closed, with run history and pause controls.
Use it when the job needs the cloud computer, browser sessions, or a human approval
card in chat.

The choice is about **where the credentials and the artifact live**, not about
features. A job that writes to the company repository belongs in the workflow
runner. A job that fills a vendor portal with no API belongs on the cloud computer.
A job that only needs files belongs in cron.

Whichever you pick, instrument it the same way: start time, end time, exit code,
artifact hash, and a heartbeat that fires when the job does not run at all.

## Testing the hands

You cannot test a headless agent the way you test a function, but you can test the
wrapper, and the wrapper is where most failures live.

Three tests worth writing before the first production run:

**The empty-input test.** Run with an empty `in/` directory. The job must fail
cleanly, with a receipt saying why, and must not produce a plausible empty report.
This catches the most common silent failure in reporting work.

**The timeout test.** Point the job at a source that hangs — a local server that
accepts and never responds. The wrapper must kill it at the ceiling, mark the run
failed, and leave a receipt. If this test leaves orphan processes, fix the wrapper
before shipping.

**The no-write test.** Run with the output directory read-only. The job must fail
loudly rather than reporting success. An agent that reports success after a failed
write is the single most dangerous behaviour in the stack, because everything
downstream trusts the artifact.

These three tests take an hour to write and they catch the failures that would
otherwise be discovered by a customer.

## Dry-run mode

Every job should support a dry run: the same inputs, the same tools for reading, but
every write replaced by a description of the write. The agent produces a plan with
diffs and exits.

Dry run is what you use when a skill changes, when a source schema changes, and when
you are onboarding a new customer. It is also the cheapest form of review: a diff
list is easier to check than an artifact, because it shows intent rather than result.

Implement it at the tool layer, not in the prompt. "Do not actually write" is a
suggestion; a tool that logs instead of writing is a guarantee.

## What the hands should never touch

Three categories, no exceptions:

**The credential store.** The agent receives scoped tokens; it never reads the vault.

**The production business records.** Reports go to staging and are promoted by a
separate step. The agent's write path and the record of truth are different paths.

**Anything with a retention obligation.** If data must be deleted on request, the
agent must not copy it into a folder nobody tracks. Retention rules apply to the
agent's workspace too.

The general principle for the entire layer: **the agent operates on copies.** Copies
can be deleted, hashed and reviewed. Originals deserve a human hand.
