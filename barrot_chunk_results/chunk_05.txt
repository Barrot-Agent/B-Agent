**6. Implementation defects that are directly observable from the source**

| Defect / questionable behaviour | Evidence in code | Potential test that would expose it |
|--------------------------------|------------------|-------------------------------------|
| **Risk level downgrade** – the logic sets `risk = "medium"` for both *auth* and *many deps*, but later the *keyword* check can raise it to `"high"`. There is **no path to `"critical"`** even though the `SecurityPosture` model defines that value. | `_assess_security` never assigns `"critical"`. | Write a test that passes a spec with `requires_auth=True` **and** `len(deps)>15` **and** a keyword; the expectation may be `"high"` (correct) but the missing `"critical"` option suggests an incomplete risk model. |
| **Duplicate assignment to `"medium"`** – the second `if len(deps) > 15` overwrites the first assignment with the same value, making the first check effectively useless. | Two separate `if` statements both set `risk = "medium"`. | A test that toggles `requires_auth` while keeping deps short will still get `"medium"`; however, disabling the `requires_auth` flag while keeping deps short yields `"low"` – the code works but the duplicated branch is dead‑weight. |
| **`_probe_package_version` and `_probe_package_deps` swallow *all* exceptions** (including `KeyboardInterrupt`, `SystemExit`). This may hide serious failures. | `except Exception:  # noqa: BLE001` catches the base class. | A test that forces `subprocess.run` to raise `KeyboardInterrupt` and asserts that the method still returns `"unknown"` – it will, but the design is arguably unsafe. |
| **`_discover_server` does not use the `self._config_path`** – the constructor stores the path but the method never reads it. This is not a bug per‑se, but a dead‑field that could mislead users. | No reference to `self._config_path` after `__init__`. | A test that injects a non‑existent config path and verifies that discovery still succeeds (showing the path is ignored). |
| **`to_json` serialises `security.known_cves` and `security.last_scanned`** but those fields are **never populated** in `_assess_security`. They will always be the defaults (`[]` and the default timestamp). | `SecurityPosture` dataclass (outside the chunk) defines those fields; `_assess_security` does not set them. | A test that checks the JSON output contains `"known_cves": []` and a `last_scanned` value – the presence of the fields may be unexpected for callers. |
| **`_TOOL_CATALOGUE` is defined but never referenced in the shown snippet** – if `_infer_tools` (not shown) relies on it, a missing key could raise `KeyError`. | No usage in the visible code. | Not directly testable from this chunk, but a future test of `_infer_tools` with an unknown category would reveal a `KeyError`. |

These defects are **detectable** with the tests outlined in section 3 (especially A, E‑G, H, J). Fixes would require code changes beyond the current task, but the tests will surface the current behaviour, making the defects visible to the maintainers.
