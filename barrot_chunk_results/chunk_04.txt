## 5. Implementation defects that are *directly observable* from the source  

| Defect / questionable behaviour | Location | Why it matters for tests / production |
|--------------------------------|----------|---------------------------------------|
| **`FilesystemMCPAdapter._impl_read_file` and `_impl_list_directory` use `Path.is_relative_to`** – this method exists only from Python 3.9 onward. If the library is ever run on 3.8 it will raise `AttributeError`. | `barrot_agent/mcp_adapters.py` | Tests on older interpreters will fail; a backward‑compatible fallback (`try: p.relative_to(allowed) ...`) would be safer. |
| **`GitMCPAdapter._WRITE_TOOLS` blocks write tools but the error message says “human approval required” while the adapter never forwards the request to the approval module** – the wording is accurate, but the behavior is a hard *reject* rather than a *defer*. If the spec expects a “pending approval” flag, this is a logic gap. | `GitMCPAdapter.call_tool` | Unit test will reveal the exact error string; if the contract changes, the test will catch the regression. |
| **`BaseMCPAdapter._wrap_call` catches *all* `Exception` and returns a generic `AdapterResult`** – swallowing `KeyboardInterrupt`, `SystemExit`, etc., may be undesirable. | `_wrap_call` | Tests that raise `SystemExit` will see it turned into a failure result rather than propagating; this is a design decision, not a bug, but worth documenting. |
| **`GitMCPAdapter.call_tool` looks up an implementation via `getattr(self, f"_impl_{tool_name}", None)`** – if a subclass accidentally defines a **public** method with the same name (e.g., `def git_status(self): …`) it will be ignored. This is a subtle naming contract that could be broken silently. | `GitMCPAdapter.call_tool` | A test that adds a *public* method named `git_status` (without the `_impl_` prefix) and verifies that it is **not** called would expose this design quirk. |
| **`FilesystemMCPAdapter._impl_search_files` is incomplete** – calling `call_tool('search_files', …)` will hit the `impl is None` guard and return “No implementation”. The public API advertises the tool, but the adapter cannot actually serve it. | `FilesystemMCPAdapter.call_tool` (when tool is `"search_files"`) | A test that calls `search_files` should assert the “No implementation” failure – this is a *missing feature* rather than a bug, but it is a mismatch between `supported_tools()` and actual capability. |
| **`BaseMCPAdapter.server_id` property returns `self._inventory.server_id` without validation** – if `inventory` is malformed (`server_id=None`), downstream code may receive `None`. No explicit guard is present. | `BaseMCPAdapter.server_id` | A test feeding a fake inventory with `server_id=None` will surface this; the library may want to raise a clearer error. |

These defects are all **observable** with the pytest cases above (or with a minimal extra test) and therefore constitute concrete regression points.
