**6. Implementation defects that are directly observable from the source**

| Location | Defect description | Why it matters for correctness / testing |
|----------|--------------------|-------------------------------------------|
| `DropRouter._safe_destination` (lines 31‑38) | References `self.repository`, which is never defined (the attribute is `self.repository_root`). The method will raise an `AttributeError` as soon as the `if not destination_path.is_absolute():` branch is taken. | Tests that call this method will fail; the bug must be fixed (replace `self.repository` with `self.repository_root`). |
| `Ternary.label` & `Ternary.color` | Direct dictionary indexing without validation – passing any integer other than ‑1, 0, 1 raises `KeyError`. The docstring implies the method “returns a label” for any ternary value, but invalid inputs cause an uncaught exception. | A robust library should raise a custom error or return a sentinel; the current behavior may break callers that accidentally pass out‑of‑range values. |
| `RepoInspectTool.execute` – `include_content` branch | Reads the whole file into memory (`content[:12000]`), but for very large files the initial `read_text` could consume massive RAM before truncation. Not a test failure, but a scalability concern. | Not a functional defect for the test suite but worth noting for production usage. |
| `RepoInspectTool.execute` – `max_files` truncation | The function silently drops files beyond `max_files` without warning; callers may assume all files were inspected. | Again a design‑choice issue; tests should verify that only the first `max_files` are returned. |
| `RepoCommandTool.execute` – `shell=True` | Allows injection if the `command` string is user‑controlled. Not a defect in the isolated test scope, but a security consideration. | No test needed; just an observation. |

from barrot_agent.ternary import Ternary, ANCHOR

def test_resolve_valid():
    assert Ternary.resolve(0.8, 0.8) == Ternary.VALID

    assert Ternary.resolve(-1.0, -0.5) == Ternary.DRIFT

def test_resolve_null():
    assert Ternary.resolve(0.2, -0.1) == Ternary.NULL

def test_gate_boundaries():
    assert Ternary.gate(ANCHOR + 0.01) == Ternary.VALID
    assert Ternary.gate(-(ANCHOR + 0.01)) == Ternary.DRIFT
    assert Ternary.gate(0.0) == Ternary.NULL

def test_confidence():
    assert Ternary.confidence() == 0.0
    assert Ternary.confidence(1, 1, -1) == 2/3
    assert Ternary.confidence(-1, -1, -1, 1) == 0.75

def test_label_and_color():
    for val, lbl, col in [(1, "VALID", "🟢"),
                          (0, "NULL", "🟡"),
                          (-1, "DRIFT", "🔴")]:
        assert Ternary.label(val) == lbl
        assert Ternary.color(val) == col
    with pytest.raises(KeyError):
        Ternary.label(2)

**6. Implementation defects that the source itself reveals (and that tests will surface)**  

| Defect / edge case | Explanation | Test that would catch it |
|--------------------|-------------|--------------------------|
| **`_recency_score` treats any truthy but non‑ISO value as “parse error” → returns 0.5** – this is intentional, but the fallback value (0.5) is the same as the “no timestamp” case, making it impossible to distinguish between “missing” and “malformed”. If the spec expected a different penalty, the current implementation is a bug. | A test feeding `"2023-13-01"` (invalid month) expects a distinct value (e.g., 0.3) – it will fail, revealing the design issue. |
| **`Improvement_targets` includes `None` in the domain set when an item lacks a `domain` key**, potentially causing *every* priority to be reported even though the corpus already has a record (albeit malformed). | Test `test_improvement_targets_none_present` (corpus item without `domain`). The current code will **still** emit all priorities – this is arguably a defect in the domain‑extraction logic. |
| **`ingest` writes the entire corpus even if the JSON file is corrupted** – `load_corpus` will raise a `json.JSONDecodeError`, bubbling up and aborting the whole engine. The engine has no graceful recovery. | A test that writes malformed JSON into the temp file, then calls `engine.ingest(...)` expects a clean exception; the failure demonstrates the missing error handling. |
| **`ingest` uses `any(item["id"] == digest …)` without guarding against missing `id` keys**. If an external process manually edits the corpus and removes an `id`, a `KeyError` will be raised. | Craft a corrupted corpus entry missing `"id"` and call `ingest`; the test will raise `KeyError`, exposing the assumption that the file is always well‑formed. |
| **`synthesize` treats missing `domain` as `"general"` – this is fine, but the return type’s `domains` mapping will contain `"general"` even when *all* items lack a domain.** If the caller expects only real domains, this could be misleading. | A test where every corpus item omits `domain`; assert that `"general"` appears exactly once per item. If the spec says it should be omitted, the test flags the behavior. |

These defects are **directly observable** with the pytest cases outlined above; they will either be caught as failing assertions (if the test encodes the intended contract) or will surface as unexpected exceptions, prompting a design discussion.
